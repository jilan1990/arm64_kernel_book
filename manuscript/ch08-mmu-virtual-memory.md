# 第八章 内存布局与 MMU 设计

## 一、概述

虚拟内存是现代操作系统最核心的机制之一。它为每个进程提供一个独立的、连续的地址空间，让进程以为自己独占整个内存。同时，虚拟内存允许内存保护、共享、写时复制等高级功能。

但在动手实现 MMU 之前，必须先把**物理内存布局**设计清楚：内核占哪里、用户程序放哪里、页分配器管哪里。v0.3 的取舍是：当前构建不启用 MMU（`mmu_init` 是占位实现），采用恒等映射的简化模型，把精力集中在进程、调度、系统调用等更关键的内核机制上；同时通过"用户槽位区 + PC 相对寻址"在无 MMU 的情况下依然实现了内核态（EL1）与用户态（EL0）的特权级隔离。这一章我们讲清楚这个设计的来龙去脉，以及未来开启 MMU 时的路径。

理解这一章的关键是分清两个容易混淆的概念：**特权级隔离（privilege isolation）**与**地址空间隔离（address-space isolation）**。特权级隔离由 CPU 的异常级别硬件保证——EL1 的代码可以访问全部地址，EL0 的代码被硬件限制（不能访问高特权系统寄存器、不能执行特权指令）；地址空间隔离则由 MMU 的页表保证——不同进程看到不同的虚拟地址映射。v0.3 实现了前者（用户程序跑在 EL0，通过 SVC 请求内核服务），暂时没有实现后者（所有地址都是物理地址，用户程序理论上能摸到内核数据）。把这两层分开理解，是本章最重要的收获。

本章代码对应最终版本 `include/mm.h`、`include/proc.h` 中的布局常量，以及 `src/mm/page_alloc.c` 里的 `mmu_init` 占位实现。

## 二、为什么 v0.3 暂不开启 MMU

### （一） MMU 的成本

开启 MMU 需要四方面工作：建立多级页表（4 级 L0-L3），为所有物理内存和 MMIO 设备建映射；配置三个系统寄存器——`TCR_EL1`（页表属性：颗粒度、地址宽度）、`MAIR_EL1`（内存类型属性）、`TTBR0_EL1`/`TTBR1_EL1`（页表基址）；为每个用户进程维护独立的 TTBR0 页表，进程切换时切换页表；处理 TLB 失效与地址翻译异常（Translation Fault）。

这些工作本身复杂度很高，而且一旦出错（映射错误、属性错误），异常极其难以调试。v0.3 的目标是先完成**进程、调度、系统调用、文件系统、网络**这条主线，MMU 留作后续扩展。

具体说，MMU 的调试难度来自"故障发生地与故障原因分离"：代码访问一个地址，实际访问的是翻译后的物理地址，而映射在哪一级页表、属性是什么、TLB 里有没有残留，任何一环出错都表现为同一个"数据中止（Data Abort）"异常。在还没有页表调试工具的教学内核里，这类问题的排查成本极高。v0.3 把 MMU 放在主线之外，让前 17 章的每一个异常都能直接对照物理地址排查，这是保证本书可跟读性的关键决策。

### （二） 恒等映射模型

v0.3 没有开 MMU，所有地址都是物理地址，也就是"虚拟地址 == 物理地址"（恒等映射）。用户程序链接在 0x48000000（用户槽位区），直接在这个物理地址运行。

```c
// 当前构建的 mmu_init：占位实现
// mmu_init stub (real implementation in chapter 8)
void mmu_init(void) {
    // Simplified: MMU not enabled in this build
}
```

注意真源中 `mmu_init` 定义在 `src/mm/page_alloc.c` 的底部，且 `kernel_main` 从未调用它（只保留了前向声明）。换句话说，v0.3 连"调用占位函数"这一步都省了——`mmu_init` 纯粹是一个接口占位，提醒读者"未来这里要开 MMU"。这是有意为之的设计决策，不是偷工减料——它让读者先理解"没有 MMU 时内核如何自洽地工作"，再理解"MMU 解决了什么问题"。

恒等映射模型的本质：既然翻译前后地址相同，MMU 开着与关着对当前代码没有可观测差异。那为什么不干脆把 MMU 打开、建一个恒等映射页表？从教学上讲，开了 MMU 就引入了页表/TLB/属性的全部复杂度，而这些复杂度在没有地址空间隔离需求时毫无收益；从调试上讲，关着 MMU 时每一个地址都可直接与物理硬件对应（用 GDB 直接查看 UART 寄存器、对照内存布局图），开着则多一层翻译。先关掉它，把主线走通；再打开它，引入隔离——这是渐进式内核开发的正确次序。

## 三、内存布局详解

### （一） 总览

```
0x00000000 ┌──────────────┐
           │     ...      │
0x08000000 │  GIC 分发器  │  MMIO（第 6 章）
0x08010000 │  GIC CPU 接口│
0x09000000 │  PL011 UART  │  MMIO（第 4 章）
0x10000000 │  virtio BAR4 │  MMIO（第 18 章，由 PCI 分配）
0x3f000000 │  (旧版 ECAM) │
0x40000000 ├──────────────┤
           │  页分配器管理 │  128MB：0x40000000 ~ 0x48000000
           │  内核镜像     │  0x40080000 起（text/rodata/data/bss/栈）
           │  内核栈页     │  进程/线程各一页
           │  slab 缓存页  │
0x48000000 ├──────────────┤
           │  用户槽位区   │  8 × 1MB：shell/hello/test 加载区
0x48800000 ├──────────────┤
           │    保留      │
0x50000000 └──────────────┘  RAM 顶（256MB）
0x4010000000  PCIe ECAM（QEMU 9.0+，64 位地址）
```

这张图值得对照第 5 章的链接脚本布局一起读。链接脚本决定内核镜像内部的段排布（text/rodata/data/bss/栈，从 0x40080000 向上）；`mm.h` 决定整个物理内存的分区（内核区/用户区）；`proc.h` 决定用户区内部的槽位划分。三层布局常量分属三个头文件，各管一段，互不重叠——读者修改布局时也应按这个职责边界去找对应的常量。

### （二） 用户槽位区设计

```c
// include/proc.h
#define USER_REGION_BASE 0x48000000UL
#define USER_SLOT_SIZE   0x100000UL
#define USER_SLOTS       8
#define USER_PROG_MAX    0xF0000UL
```

每个用户进程占用一个 1MB 槽位：低地址放代码（从槽底开始），栈从槽顶向下生长。槽位区在页分配器管理范围（128MB）之外，所以：

- 页分配器永远不会把用户程序占用的页分配给别人；
- 用户程序访问越界时，最多碰到相邻槽位或保留区，不会直接踩坏内核数据结构。

`USER_PROG_MAX 0xF0000UL` 是单个用户程序的最大字节数（约 960KB），略小于 1MB 槽位——留出槽顶的 64KB 给用户栈。第 10 章 `proc_fork` 拷贝用户栈时"上限半槽 0x80000"，与这个常量配套：代码从槽底向上、栈从槽顶向下，两者在槽内相向生长，`USER_PROG_MAX` 和栈拷贝上限共同保证它们不会互相撞上。

内核通过 `proc.c` 计算槽位：

```c
int slot = (int)((p - proc_table) % USER_SLOTS);
unsigned long base = USER_REGION_BASE + (unsigned long)slot * USER_SLOT_SIZE;
```

`p - proc_table` 是进程在进程表中的下标，取模 8 得到槽位号，进程天然映射到固定槽位。这个"进程表下标 → 槽位号"的映射有一个好处：进程与其内存区域一一对应，无需额外的分配记账。进程表最多 64 个进程（MAX_PROCS=64），但槽位只有 8 个，所以同一时刻最多 8 个进程拥有用户内存——这是无 MMU 模型的内在容量约束，也是"槽位复用"（一个进程退出后槽位可被新进程占用）的设计由来。`create_user_process` 中配套的还有：

```c
frame->elr_el1 = base;                  // 入口 PC = 槽位基址
frame->sp_el0 = base + USER_SLOT_SIZE;  // 用户栈顶 = 槽位顶部
```

### （三） 为什么用户程序能"搬到任何槽位"运行

v0.3 的关键设计：**用户程序用 PC 相对寻址编译**（`-fno-pic` 下 GCC 对函数调用/数据访问默认生成 ADR/ADRP 指令，以 PC 为基准计算地址），并配合用户链接脚本：

```ld
/* 用户程序链接脚本：链接基址 0x48000000。
   实际加载槽位不同也没关系：代码使用 PC 相对寻址（ADRP/BL），
   入口 PC 和栈指针由内核按槽位基址重设。 */
ENTRY(_start)

SECTIONS {
    . = 0x48000000;
    .text : { *(.text.start) *(.text) *(.text.*) }
    . = ALIGN(8);
    .rodata : { *(.rodata) *(.rodata.*) }
    . = ALIGN(8);
    .data : { *(.data) ... }
    . = ALIGN(8);
    __bss_start = .;
    .bss : { *(.bss) ... }
    __bss_end = .;
}
```

链接基址 0x48000000 只是为了让链接器生成正确的相对偏移；实际被加载到哪个槽位（0x48000000、0x48100000、……）由内核决定。只要程序自身不做绝对地址假设，任何槽位都能跑。`create_user_process` 设置 `frame->elr_el1 = base`（入口 PC = 槽位基址），`frame->sp_el0 = base + USER_SLOT_SIZE`（栈顶 = 槽位顶部）。这就是"无 MMU 的进程隔离"：**隔离靠物理分区，而非地址翻译**。

用一个具体例子验证这个机制。`user/test.S` 里取字符串地址用的是：

```asm
adr x1, msg
```

`adr` 是 PC 相对指令：`x1` 得到的是"msg 相对当前 PC 的偏移"。程序被复制到 0x48000000 时，`adr` 算出 0x48000000+偏移；被复制到 0x48200000 时，同样的指令算出 0x48200000+偏移——**同一份字节码，在任何槽位都指向自己的数据**。这就是第 3 章讲的 PC 相对寻址的实践价值。可以用 `aarch64-linux-gnu-objdump -d user/hello.elf` 验证：反汇编里函数调用是 `bl` 形式的 PC 相对偏移，数据访问是 `adrp` + `add :lo12:` 组合，几乎看不到绝对地址常量。

## 四、无 MMU 下的特权级隔离

没有 MMU，地址空间不隔离，但特权级仍然由硬件隔离。EL0（用户态）与 EL1（内核态）的边界由异常级别保证：用户程序运行在 EL0，`SVC` 指令触发同步异常，CPU 自动陷入 EL1；陷入后内核在 EL1 执行系统调用处理，完成后 `eret` 回到 EL0；EL0 下无法访问系统寄存器（如 `msr vbar_el1` 会触发 UNDEFINED 异常）、无法执行特权指令。三点合起来构成"用户态必须借道内核"的硬件框架——没有这层隔离，用户程序可以直接篡改内核状态，操作系统概念无从谈起。

这套机制与 MMU 无关——它由 CPU 异常模型（第 6 章）提供。所以 v0.3 的用户程序"碰不到内核"是**行为约定**（正确编写的用户程序只通过系统调用请求服务），而不是**硬件强制**（用户程序如果故意读 0x40080000 的内存，无 MMU 时真的能读到）。理解这个区别很重要：真内核（Linux）需要 MMU 才能把"约定"升级为"强制"；v0.3 的教学价值恰恰在于先演示"约定"这一半，让读者意识到地址空间隔离的必要性，再在下一节看到它如何被 MMU 补上。

用户程序"请求内核服务"的唯一通道是 `svc #0`，系统调用号放 X8，参数放 X0-X5。内核的 `do_sync_handler` 按 ESR.EC==0x15 识别 SVC，查 `syscall_table[number]` 分发（第 12 章）。这张"唯一入口表"就是无 MMU 系统的安全边界：只要内核只信任 SVC 入口、严格校验参数（比如 `console_write` 对 fd 越界的检查、`sys_read` 对缓冲区地址的检查），用户程序就只能在约定范围内行动。

## 五、未来开启 MMU 的路径

如果未来要开启 MMU，需要做以下工作（这也是 v0.3 留下 `mmu_init` 接口的原因）：一是内核页表（TTBR1），建立 0x40000000~0x50000000 物理内存和 MMIO 设备的恒等映射，内存类型设为 Normal（RAM）和 Device-nGnRnE（MMIO）；二是用户页表（TTBR0），每个进程建立独立的 L1/L2 页表，把用户槽位区映射到虚拟地址空间（例如 0x00000000~0x00100000），进程切换时切换 TTBR0；三是隔离收益，用户程序只能看到自己的虚拟地址空间，访问 0x40000000（内核区）会产生 Translation Fault，从而获得真正的进程隔离；四是 AArch64 页表格式，页表项的低位是属性（bit 0 有效位、bit 1 表/块、bit 6-2 权限等），高 36 位是下一级页表或块的物理地址，需要配置 `MAIR_EL1` 定义 Normal/Device 内存属性索引、`TCR_EL1` 定义 4KB 颗粒度和 48 位地址宽度。

开启 MMU 的具体步骤（按硬件手册顺序）：先把页表物理地址写入 TTBR0/TTBR1 → 配置 MAIR（内存属性）→ 配置 TCR（翻译控制）→ `dsb sy` 确保配置生效 → `mrs` 读 SCTLR_EL1 置 M 位 → `isb` 使新配置生效。必须用 DSB+ISB 组合：DSB 保证前面的页表写和配置写都完成，ISB 保证后面的取指/访存使用新的翻译状态。漏掉任何一个屏障，MMU 开启后的第一条指令可能还在用旧翻译，行为未定义。

## 六、MMU 机制原理（背景知识）

即便当前未启用，理解 AArch64 地址翻译仍然必要，因为它是 Linux 内核工作的基础。第一个概念是 TTBR0_EL1 与 TTBR1_EL1：两个翻译表基址寄存器把虚拟地址空间分成两半——TTBR0 管低地址（用户），TTBR1 管高地址（内核）。内核切换进程实际就是切换 TTBR0；用两个寄存器而不是一个的原因在于，内核页表（TTBR1）可以永久驻留，进程切换时只需换 TTBR0、不需要同时重建内核映射——这是 Linux 内核地址空间"每个进程都看到同一个内核"的实现基础。第二个概念是 4KB 颗粒度四级页表：L0（512 项，覆盖 512GB）、L1（512 项，覆盖 1GB）、L2（512 项，覆盖 2MB）、L3（512 项，覆盖 4KB），缺省配置下每个虚拟地址 48 位，页表逐级查询 9 位索引。为什么是 4 级：48 位虚拟地址按每级 9 位索引 + 12 位页内偏移逐级查询，若把 48 位全部放进一级需要 2^36 项，不可能——多级页表本质是用"逐级索引"换取"稀疏映射"，大多数地址空间根本用不到，只有用到的页才需要分配页表项，这也是第 7 章位图分配器的直接应用（每级页表占一页，由页分配器提供）。第三个概念是 TLB（Translation Lookaside Buffer）：页表查询的缓存，进程切换后必须 `tlbi vmalle1` 冲刷整个 TLB，否则旧进程的映射残留导致访问错误地址；TLB 失效开销是进程切换的隐藏成本，所以现代内核用 ASID（地址空间标识符）让 TLB 同时缓存多个进程的映射，切换时不必全冲刷。第四个概念是 MAIR_EL1：内存属性指示寄存器，把页表项中的 3 位属性索引映射为具体的内存类型（Normal 可缓存 / Device 不可缓存）；MMIO 设备（UART、GIC）必须标 Device——CPU 对 Device 内存不做缓存、不重排、单次访问语义，这与第 4 章 volatile 的要求一致，只是由硬件层面强制执行。

这些内容为读者将来阅读真实内核（Linux、XNU）铺路。本书第 19 章给出了进一步学习路径。

## 七、延伸：恒等映射与未来移植的衔接

一个容易困惑的问题是："恒等映射下，虚拟地址等于物理地址，那第 18 章 PCI 的 64 位 ECAM 地址 0x4010000000 怎么访问？"答案是：QEMU 把 PCIe ECAM 配置空间映射在这块 64 位物理地址，恒等映射下内核直接按这个地址读即可（无需页表）。未来开启 MMU 时，内核页表必须为它建立 Device 内存映射（属性 Device-nGnRnE），否则 MMIO 访问会被 CPU 缓存污染或触发对齐异常——这是"开 MMU"清单里最容易漏的一项。同理，UART（0x09000000）、GIC（0x08000000）、virtio BAR（0x10000000）都要在建页表时逐一登记内存类型。读者可以预先在纸上列出 v0.3 用到的全部 MMIO 地址（第 4/6/14/18 章各设备），这就是未来 TTBR1 内核页表的初始条目清单——把本章"开启 MMU 的路径"从抽象步骤变成具体表格，是迈向真实内核移植的第一步。

此外还有一个容易被忽视的衔接点：用户槽位区 0x48000000~0x48800000 在恒等映射下是"物理地址即虚拟地址"，将来若把用户虚拟地址空间设成从 0x00000000 开始（Linux 的惯例），槽位区就需要页表映射到新的用户虚拟地址，`proc.c` 里所有 `USER_REGION_BASE` 的用法（槽位计算、异常帧 sp_el0、fork 的 delta 平移）都要改成"虚拟地址计算"——读者可以提前在注释里标出这些位置，将来移植时按图索骥，避免在无 MMU 的代码里混入对虚拟地址的假设。本章到此，读者应能完整回答"v0.3 为什么能工作"与"开 MMU 要动哪里"两个问题，并带着这两张清单进入后续的进程、设备与网络章节——那里的每一个"地址"与"内存"决策都建立在本章的地图之上。

## 八、小结

本章澄清了五件事：v0.3 暂不开启 MMU 的原因（聚焦主线 + 恒等映射模型）；128MB 页分配器管理区与用户槽位区的隔离设计；用户程序 PC 相对寻址 + 槽位加载的原理（`USER_PROG_MAX` 与栈上限的配套）；无 MMU 下的特权级隔离（EL0/EL1 + SVC 唯一入口）；未来开启 MMU 的具体路径与 AArch64 地址翻译背景（TTBR/TCR/MAIR/TLB/四级页表）。五件事环环相扣：先回答"为什么不开"，再讲清"不开时如何隔离"，最后给出"开时要动什么"。

v0.3 的隔离结论：没有 MMU 也能实现内核/用户特权级隔离（EL1/EL0 由硬件保证，系统调用是唯一入口），只是地址空间不隔离。读者应理解这两者的区别：**特权级隔离靠异常级别，地址空间隔离靠 MMU**。

## 九、练习

练习一，修改 `USER_SLOT_SIZE` 为 2MB，观察进程表槽位计算是否仍然正确——提示：槽位区总大小 = `USER_SLOTS × USER_SLOT_SIZE`，改大后可能超出保留区边界，需要同步调整 `MEMORY_SIZE` 或槽位区起点。练习二，阅读 `create_user_process` 的槽位计算，思考为什么 `(p - proc_table) % USER_SLOTS` 能保证槽位唯一——进程表下标天然唯一，取模只是把它折叠进 8 个槽位，两个进程同槽时按创建顺序互斥。练习三，研究 AArch64 TTBR0/TTBR1 的地址划分，画一张 48 位虚拟地址空间的分配图——TTBR0 覆盖地址空间低半，TTBR1 覆盖高半，划分点由 TCR 的地址宽度字段决定。练习四，用 `aarch64-linux-gnu-objdump -d user/hello.elf` 反汇编，找出所有 `adrp`/`bl` 指令，验证用户程序确实不依赖绝对地址——这是第 3 章 PC 相对寻址的实证。练习五，修改 `mmu_init` 让它打印一条日志（如 `mmu_init: skipped (identity mapping)`）再观察启动日志，确认 v0.3 的 `kernel_main` 从未调用它——理解"接口占位 vs 实际启用"的区别。
